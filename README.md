# WINDOW.exe

오래된 컴퓨터에 남겨진 전 사용자의 흔적과 창 너머 공간을 조사하며, 정체불명의 프로그램을 삭제하고 살아남는 아날로그 호러·미스터리·퍼즐 어드벤처 프로젝트다.

## 문서 안내

상세 문서는 `docs/`에 모으고, 루트에는 이 안내 문서와 [AGENTS.md](AGENTS.md)를 둔다. AGENTS.md는 개발 전 문서 확인과 개발 중·후 문서 갱신 절차를 정한다.

각 내용은 아래 담당 문서 한 곳에서 관리한다. 다른 문서에는 필요한 연결만 남긴다.

| 문서 | 역할 | 이곳에서 다룰 내용 |
|---|---|---|
| [PROJECT_CONTEXT.md](docs/PROJECT_CONTEXT.md) | 프로젝트 배경 | 게임잼, 행사 조건, 채점 기준, 제작 목표의 배경 |
| [GDD.md](docs/GDD.md) | 순수 게임 기획 | 플레이 경험, 세계관, 등장인물, 규칙, 퍼즐, 엔딩, 연출, 기획 미정 사항 |
| [IMPLEMENTATION_CHECKLIST.md](docs/IMPLEMENTATION_CHECKLIST.md) | 구현 작업과 상태 | 담당, 오늘 할 일, 후속 작업, 리소스 제작·적용, 완료 조건과 체크 |
| [DEVELOPMENT.md](docs/DEVELOPMENT.md) | 개발 가이드 | Unity 환경·프로젝트 열기, Git 공유, 시스템 연결, 데이터·UI 구조, 구현 방식 |
| [PRODUCTION_PLAN.md](docs/PRODUCTION_PLAN.md) | 제작·시연 계획 | 목표 분량, 우선순위, 축소안, 일정, 발표·시연 순서 |
| [CHANGELOG.md](docs/CHANGELOG.md) | 변경 이력 | 결정 변경의 이유와 날짜, 문서 이동, 이전 기록 |

## 어디부터 읽을까

데스크톱을 실행하려면 Unity에서 `Assets/Scenes/Desktop.unity`를 열고 Play Mode를 시작한다. 프로젝트를 여는 방법과 창 시스템 연결은 [개발 가이드](docs/DEVELOPMENT.md)에서 확인한다.

`Assets`는 `Scripts`, `Editor`, `Tests`, `Prefabs`, `Data`, `Scenes`, `Art`, `Settings`처럼 역할별로 나누고, 각 역할 아래에 `Desktop` 같은 기능 폴더를 둔다. 새 파일의 위치와 Git 공유 규칙은 [개발 가이드의 Assets 폴더 배치](docs/DEVELOPMENT.md#assets-폴더-배치-확정--사용자-지정)를 따른다. 폴더 정리 후 확인 결과와 공유 상태는 [체크리스트 10장](docs/IMPLEMENTATION_CHECKLIST.md#10-assets-역할별-정리와-재검증)에서 확인한다.

기본 데스크톱 구현·제공 아트·테스트는 `fab196a`로 공유했다. 이후 영역 선택·묶음 이동과 역할별 폴더 정리도 현재 코드에 포함되어 있다. 더블클릭은 고정 식별자의 열기 요청을 전달하며, 실제 창 생성·최소화 복원은 팀원 시스템 연결 후 동작한다. 최초 공유 시점의 검증 결과는 [구현 체크리스트 8장](docs/IMPLEMENTATION_CHECKLIST.md#8-1030-구현검증-결과와-공유-범위)에서 확인한다.

빈 곳 클릭은 전체 선택 해제, 선택된 아이콘 드래그는 묶음 이동, Escape는 진행 중 조작 취소다. 추가 검증 결과는 [체크리스트 9장](docs/IMPLEMENTATION_CHECKLIST.md#9-영역-선택묶음-이동-추가-구현-결과), 현재 경로의 재검증은 10장에서 확인한다.

- 게임이 어떤 내용인지 보려면 **GDD**를 읽는다.
- 지금 본인·팀원이 무엇을 만들지 보려면 **구현 체크리스트 2~4장**을 읽는다.
- 프로젝트를 열거나 두 시스템을 연결하려면 **개발 가이드**를 읽는다.
- 행사 조건과 평가 이유는 **프로젝트 배경**, 남은 시간과 시연 준비는 **제작·시연 계획**에서 확인한다.

## 문서 관리 규칙

- **[확정]**은 기존 합의나 사용자가 지정한 내용이다. **[제안]**은 합의 전인 안, **[미정]**은 결정이 필요한 질문이다. 문서를 옮겼다는 이유로 상태를 바꾸지 않는다.
- 확정 여부는 기획·요구사항의 상태이고, 체크박스는 실제 작업의 완료 확인 상태다. 기획 확정만으로 완료 체크하지 않는다.
- 내용이 바뀌면 위 표의 담당 문서를 수정한다. 구현 완료 체크는 **구현 체크리스트에서만** 갱신한다.
- GDD에는 담당·날짜별 할 일·기술 구조를 넣지 않는다. 기획 미정 사항은 GDD에, 구현 방식의 제안은 개발 가이드에 남긴다.
- 중요한 결정이나 범위가 바뀌면 담당 문서를 고치고 **CHANGELOG**에 날짜와 이유를 기록한다. 단순 완료 체크마다 이력을 추가할 필요는 없다.
- 로컬 시험 구현·원문의 제작 기록과 공유 프로젝트에서 확인한 완료 상태를 구분한다.
