# WINDOW.exe — 제작·시연 계획

> 역할: 목표 분량, 작업 우선순위, 일정과 발표·시연 순서를 관리한다.
> 기준일: 2026-10-31. 별도 표기가 없는 계획은 **[제안]**이다.
> 행사 조건은 [프로젝트 배경](PROJECT_CONTEXT.md), 담당·진행 상태는 [구현 체크리스트](IMPLEMENTATION_CHECKLIST.md)에서 관리한다.

## 현재 작업 운영 [확정 — 2026-10-31 사용자 지시]

핵심 플레이·시연 안정성을 우선하고, 작은 수정은 요청한 결과와 관련 확인으로 마무리한다. 부가 연출 때문에 공통 구조 변경·반복 전체 검수가 필요해지면 먼저 단순화·축소 가능성을 판단한다. 구체적인 검증 선택과 Unity 직렬 실행은 [AGENTS.md](../AGENTS.md#작업-시간과-범위)를 따른다.

현재 미완료 범위는 체크리스트를 먼저 보고, 새 작업에 관련된 단계만 선택한다. 이미 통과한 착수 단계를 처음부터 반복하지 않는다. 초기 데스크톱·영역 선택·창 호환·QA 수정의 상세 순서는 [초기 제작 순서 기록](history/PRODUCTION_PLAN_HISTORY.md)에 보존했다.

## 1. 목표와 우선순위

핵심 플레이가 실제로 작동하는 짧은 한 판을 목표로 한다. **[확정 — 현재 설정]** 앞 퍼즐의 열쇠 획득에서 복원 함정과 보스전을 거쳐, 직접 휴지통 비우기로 프로그램과 희생자들을 삭제한다. 2페이즈 피격은 다운로드를 유지한 채 즉시 리스폰하고, 다운로드가 완료되면 별도 배드 엔딩으로 종료하며 리스폰하지 않는다. 구출·자리 교환 경로는 만들지 않는다.

**[확정 — 사용자 답변]** 보스전은 1·2페이즈 모두 목표로 하고 2페이즈부터 확보한다. 구현 우선순위와 축소 원칙은 [보스전 기획 9장](BOSS_FIGHT.md#9-우선순위-제안), 담당·완료 조건은 체크리스트 18장, 착수 후 단계는 이 문서 12장을 따른다. **보스전은 사용자 명령으로 구현에 착수한 상태이며, 현재 완료·미완료 범위는 체크리스트 18장을 따른다.**

## 2. 범위 조정 [제안]

- 매 단계에 시작·전진·회피·실패/재시작·성공이 있는 작은 플레이 흐름을 확보한다.
- 보스전 일정이 부족하면 1페이즈를 빼고 2페이즈를 남기는 기존 축소안을 적용한다. 필요한 조작 안내는 2페이즈 유언에서 전달한다.
- 후반 눈 2개·보스 직접 사격·바퀴당 속도 증가·분위기 연출·사운드 다듬기는 보스전 기획의 선택 범위다.
- 앞 퍼즐의 파일 조사·비밀번호·엿보기 해법은 별도 담당이 정한다. 과거 반환 순서를 현재 삭제의 선행 조건으로 복원하지 않는다.
- 보스전 직전 연출·성공 엔딩·다운로드 완료의 별도 배드 엔딩 장면은 다른 담당의 범위다. 보스전은 진입/성공/배드 엔딩 신호와 표시 인계를 연결한다.
- 일반 창의 시작 메뉴·트레이·시계·앱 고정 같은 후속 기능을 보스전의 선행 조건으로 잡지 않는다.
- 실제 OS 종료 감지나 작동하는 작업 관리자·전원 UI는 범위에 넣지 않는다.
- 공통 글꼴과 CRT의 기존 구현을 사용하되, 새 유언·위험 신호의 가독성과 실제 게임 상태 연결은 별도로 확인한다.

## 4. 발표·시연 흐름 [제안]

1. 파일 조사·엿보기로 창이 공간을 비춘다는 점과 열쇠 획득을 짧게 보여 준다. 앞 퍼즐의 확정 해법은 담당과 맞춘다.
2. 휴지통 복원으로 강제 다운로드가 시작되고 눈알 연출로 함정이 드러난다.
3. 보스전에서 창을 늘리고 휴지통을 끌며 전진하는 조작을 보여 준다. 두 페이즈는 보스전 기획의 목표 길이 안에서 시연한다.
4. 복원 취소 뒤 플레이어가 직접 휴지통 비우기를 실행하고 정상 바탕화면으로 돌아오는 성공 엔딩으로 마무리한다.
5. 리허설·개발용으로는 보스전 바로 시작·페이즈 건너뛰기·무적·다운로드 멈춤을 준비한다. 실제 발표 사용 여부는 리허설에서 정하며 활성 표시는 숨기지 않는다.

빠른 포획으로 일자 벽을 생략할 수 있으므로, 벽 회피를 보여 줄 리허설에서는 임계값을 넘은 뒤 벽을 기다려 최소화한다. 이를 위해 실제 게임 진행을 강제로 잠그지는 않는다.

### 질의 대비 한 줄 답변

### 바로 착수할 단위

사용자 요청으로 **최소 작업 표시줄 UI와 창 연결**에 착수했던 순서를 아래에 보존한다. 1~4의 임시 단계 결과는 체크리스트 11장, 이후 실제 창 연결인 5의 일반 흐름은 12장, 추가 검수에서 발견한 미해결 예외는 15장에서 관리한다. 현재 작업을 임시 제공자 단계로 되돌려 해석하지 않는다. 창의 이동·크기·최소화·최대화와 활성 상태는 실제 창 시스템이 관리한다.

| 순서 | 착수 단위 | 다음으로 넘어갈 기준 |
|---|---|---|
| 1 | 연결 계약 초안·정책 정리 | 임시 제공자와 UI가 사용할 식별자·조회·알림·요청 계약을 정하고, 팀원 API에서 미확인인 대응 항목을 남긴다. 창 구현 완료를 기다리지 않고 2~4로 진행 가능 |
| 2 | 공통 작업 영역·하단 바 | 공통 영역을 계산해 데스크톱에 먼저 적용하고 창 시스템의 연결 지점을 준비한다. 기존 공유 씬에 구성·참조를 보존해 추가하며 실제 창 제약 적용은 5에서 확인 |
| 3 | 목록과 버튼 동기화 | 미리 열린 창부터 등록하고 변경·제거·재구독·초기화에 맞춰 표시한다. 버튼 수 초과와 긴 제목도 접근 가능하게 한다 |
| 4 | 활성화·최소화·복원 | 클릭 직전 상태와 허용 조작에 따라 요청하고 확정 상태를 표시한다. 다음 활성 창·최대화 복원·요청 거부를 확인한다 |
| 5 | 실제 창 통합·회귀·빌드 조작 | 임시 수신기를 실제 창 어댑터로 연결하고 기존 데스크톱 동작을 회귀 확인한다. 두 해상도의 공유 씬과 Windows 실행 빌드에서 실제 입력을 확인한다 |

연결 계약과 초기 수치는 [개발 가이드](DEVELOPMENT.md#작업-표시줄-연결-계약-제안), 상세 작업·검증은 [체크리스트 2-2장](IMPLEMENTATION_CHECKLIST.md#2-2-다음-착수--최소-작업-표시줄-제안)을 따른다. 팀원 창이 준비되기 전에는 같은 계약의 임시 상태로 2~4를 진행할 수 있으나, 실제 창 통합과 빌드 조작 확인은 별도로 남긴다. 게임 재시작·종료 화면과 엿보기 단서 도달 검증은 해당 기능 통합 시 이어서 확인한다.

팀원 API 대조와 Git 병합은 완료했고, 렌더링과 최소 입력 차단을 준비한 뒤 어댑터를 먼저 연결하고 다중 창 입력을 확장한다. 다음 구현은 8장 순서로 진행한다. 현재 임시 단계의 결과는 [체크리스트 11장](IMPLEMENTATION_CHECKLIST.md#11-작업-표시줄-임시-제공자-단계-구현검증), 병합 검토는 12장에서 관리한다.

**[확정 — 사용자 지정]** 별도 창 숨김은 첫 구현에서 보류하고 기록만 남긴다. 모달 소유 창의 활성화 요청을 해당 모달로 전달하는 예외는 명시하며 소유 창 최소화는 거부한다. 전체 조작 잠금·제거된 창에는 예외를 적용하지 않는다. 세부 계약의 원본은 개발 가이드, 보류 기록과 완료 확인은 체크리스트에서 관리한다.

이 최소 작업 표시줄 단계에서는 시작 메뉴·트레이·시계·앱 고정·전환 애니메이션을 후순위로 두었다. 이후 시작 버튼 요청의 추가 계획은 9장을 따른다. 검수 보완은 기존 최소 범위의 동작·연결·완료 조건을 구체화한 것이며 새 게임 규칙이나 담당의 확정을 뜻하지 않는다.

이 흐름을 확인한 뒤 **진행 상태 + 메모·설명서·사진 데이터와 비밀번호 판정**으로 넘어간다. 초기 검증용 암호 `1030`과 내용은 GDD 7-1장의 제안으로 유지한다. 기존 창 연결 경로에 사진 잠금 화면을 얹고, 데이터·판정 검증과 실제 화면 통합 확인은 구분한다.

게임 콘텐츠의 첫 작은 흐름은 **메모 열기 → 날짜 확인 → 사진 비밀번호 해제 → 닫고 다시 열어 해제 상태 확인**이다. 그다음 게임의 핵심 차별점인 엿보기로 이어간다. 시작 오류·실행 전 경고는 게임 진입과 프로그램 실행을 연결할 때 함께 넣고, 긴 도입 연출은 후속으로 다듬는다.

### 연결 전에 맞출 사항

- 팀원과 창 연결 계약·표시 및 허용 조작 정책·WindowLayer·공통 작업 영역·Canvas 배율을 맞춘다. 실제 조회·알림·요청 형식과 기존 열기 이벤트의 대응은 [개발 가이드](DEVELOPMENT.md#작업-표시줄-연결-계약-제안)를 따른다.
- 엿보기 창의 최대화·최소화·리사이즈 허용 범위는 GDD의 미정 사항이다. 우선 기본 크기와 창 이동으로 단서에 도달하는 검증을 만들고, 허용 범위는 통합 전에 정한다.
- 휴지통은 현재 아이콘 겹침 검사에서 일반 충돌 대상이다. 게임의 드롭 의도를 판정한 뒤 일반 배치 확정을 처리하도록 분리한다. **[제안]** 첫 삭제 구현은 WINDOW.exe 하나만 선택해 끌었을 때로 제한하고, 다중 선택 드롭은 삭제하지 않고 전체 복귀·안내한다. 영구 배치에서 아이콘 겹침을 허용하지 않는다.
- 1~6의 콘텐츠·퍼즐·엔딩 세부 규칙은 GDD의 기존 [제안]·[미정] 상태를 유지한다. 작업 순서 정리만으로 기획을 확정하지 않는다.

### 한 판을 연결한 뒤 할 일

구출 분기의 자리 교환 배드 엔딩, 오염도·시선 위협, 사운드·글리치 연출은 후속 순서로 둔다. 제공 폰트 적용·추가 아트 다듬기는 실제 콘텐츠 화면을 읽을 수 있는지 확인하며 진행한다. Ctrl·Shift·Ctrl+A, 우클릭 메뉴·격자 정렬·위치 영구 저장은 계속 후순위로 유지한다.

## 9. 좌하단 시작 버튼 추가 [제안]

최초 메뉴 항목은 기존 메모·사진·인터넷으로 제한하는 안이다. 전원·강제 종료·게임 재시작과 검색·앱 고정·하위 메뉴는 별도 작업으로 남겨 핵심 게임 제작 분량이 커지지 않게 한다. 세부 기술 규칙은 [개발 가이드 12장](DEVELOPMENT.md#12-좌하단-시작-버튼-구현-계획-제안), 완료 확인은 [체크리스트 14장](IMPLEMENTATION_CHECKLIST.md#14-좌하단-시작-버튼-구현-계획--2026-10-31)에서 관리한다. 이번 요청에서는 계획 문서만 갱신한다.

## 11. 전체 화면 CRT 노이즈 적용 순서 [제안]

2026-10-31 작성한 제공 소스 개선안을 후속 사용자 지시에 따라 구현에 착수했다. 아래는 진행 순서의 원안이며 후속 검토에 따라 4단계에 측정용 Development Player 생성, 5단계에 최종 빌드를 구분했다. 실제 완료·남은 검증은 체크리스트 16장에서 관리한다. 기존 창·작업 표시줄·공통 글꼴과 QA 수정 결과를 기준으로 삼고, 게임 한 판·시작 버튼의 우선순위나 시간별 마감을 새로 확정하지 않는다.

| 순서 | 작업 단위 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 0. 소스·출력 기준선 | 로컬 제공 소스 보존, 역할별 경로·공유 의존성 정리, 실제 URP 셰이더 확인 | 컴파일·단일 전체 화면 출력과 기존 화면 보존 확인. 조회 시간초과를 통과로 처리하지 않음 |
| 1. 제어 수정 | 기본 단계 보간·명시적 Spike 합성과 유지/복귀 중 재호출·실제 시간·초기화 구현 | 설정 시간 도달과 최신 기본값 복귀가 일관되고, 복귀 중 재호출은 즉시 Spike와 새 유지 시간으로 전환 |
| 2. 설정·수명 | 표시 전 검증, 컴포넌트/오브젝트 비활성 숨김·재활성, 재질·단일 인스턴스·재실행 정리 | 첫 표시와 재표시에 최신 목표/해상도를 적용. 두 Reload를 끈 연속 Play에도 시간·전역 참조·재질이 누적되지 않음 |
| 3. 씬 통합 | 재질·프리팹·기존 씬 갱신·신규 생성 연결, 표시 순서·입력 통과 적용 | 현재 모든 게임 화면 요소에 효과가 겹치고 입력/Secondary 캡처 보존. 반복 갱신 중복 없음 |
| 4. 표시·회귀·비용 | 두 해상도/비율 변경, 프리셋 조정, 기존 조작·시간/수명 시험, 측정용 Development Player 생성 후 CPU/GPU 비교 | 가독성과 입력 회귀 통과. 개발 가이드 14-7장의 초기 예산을 판정하고 미측정/미달·최종 품질을 구분해 기록 |
| 5. 최종 빌드·인계 | 최종 채택 품질의 Desktop 지정 빌드·셰이더 포함·실행 파일 조작, 메타/공유/문서 확인 | 검증한 환경과 남은 게임 상태 연결을 나눠 보고하며 미확인 항목을 완료 처리하지 않음 |

가독성 문제는 기본 노이즈·비네트·Spike 강도를 조정한다. 성능 문제는 계산 생략 → Simple 경로 → 품질 Off의 실제 비용 감소로 대응하며 강도만 줄여 해결됐다고 보고하지 않는다. 품질 Off는 단계 0과 별개이고 게임 오염도 값을 바꾸지 않는다. CPU/GPU 측정 구간·프레임 예산·미측정 처리의 원본은 [개발 가이드 14-7장](DEVELOPMENT.md#14-7-성능-측정예산저비용-대응-제안)을 따른다.

휘어짐·색수차·화면 찢김을 같은 작업에 추가해 범위를 넓히지 않는다. 약한 기본 효과와 제어 API를 먼저 검증하고, 게임 진행 시스템이 준비되면 오염도 전달·재시작 초기화·실패/엔딩 화면의 적용 범위를 별도로 연결한다. 시선 위협 미채택 시 오염도 0을 유지하는 기존 제안도 그대로다.

기술 계약과 초기 시간값·파일 배치는 [개발 가이드 14장](DEVELOPMENT.md#14-전체-화면-crt-노이즈-구현-계획-제안), 담당 제안·작업·완료 조건은 [체크리스트 16장](IMPLEMENTATION_CHECKLIST.md#16-전체-화면-crt-노이즈-구현-계획--2026-10-31)에서 관리한다. 이 계획의 UI 검증을 게임 오염도·게임 오버 구현 완료로 바꾸지 않는다.

0단계의 기준선 기록은 [체크리스트 17-1장](IMPLEMENTATION_CHECKLIST.md#17-1-tmp-참조-손상-복구--2026-10-31)의 127개 중 117개 통과·기존 실패 10개를 출발점으로 삼고, 착수 후 새 실행과 간헐 실패를 체크리스트 18장에 구분한다. 보스전 작업에서 기존 별도 실패를 숨기거나 담당 범위를 임의로 확장하지 않는다. 현재 0a의 Windows 입력 검증과 0b의 기반 호환 시험을 통과하여 1~2단계의 2페이즈 실행기·벽·공격 순서까지 구현·자동 검증했다. 이후 1페이즈 경로를 모델/원본 입력 재생으로 먼저 검증하고 숨은 층·오염·페이즈 전환과 인계 API까지 연결했다. 현재는 수동 피드백으로 1페이즈의 면적·지정 경로 제한을 제거하고 눈 배치를 재검증한다. 이후 5단계의 수동 플레이·가독성과 다른 담당의 앞뒤 연출 통합을 이어 간다. 0a의 기술안이 실제 수집/정밀도 검증을 통과하지 못하면 그 계약을 보정한 뒤 1단계로 넘어간다.

기존 인터넷·열쇠의 ID/등록 불일치는 [체크리스트 17-2장](IMPLEMENTATION_CHECKLIST.md#17-2-인터넷열쇠의-기존-연결-불일치-후속--2026-10-31)에서 기존 담당의 후속으로 관리한다. 0b는 보스전의 기술 경계를 먼저 확인하는 단계이며 앞 퍼즐 전체를 대신 구현하는 범위가 아니다. 전용 카메라/RT의 작은 표시 검증은 3단계의 전체 숨은 층 제작 전에 수행한다. 정리 시 이전 화면·카메라·CRT 제어를 되살리지 않는 조건까지 [개발 가이드 17-9장](DEVELOPMENT.md#17-9-기존-기능과의-호환-계약-제안)에 따라 검증한다.

0단계에서 1페이즈 경로의 수치 충돌을 먼저 찾고 3단계 시작 시 단순 도형의 실제 조작으로 확인한 뒤 전체 표시를 제작한다. 2페이즈를 먼저 확보하는 우선순위는 유지한다. 검토 후 사용자 결정의 원본은 [BOSS_FIGHT 13-1장](BOSS_FIGHT.md#13-1-사용자-답변으로-확정한-사항--2026-10-31), 세부 경합·시간·인계 검증 방식은 개발 가이드 17장에 둔다.

**축소 기준:** 2단계를 먼저 시연 가능한 상태로 보존한다. 남은 일정으로 1페이즈 경로와 전체 검증을 함께 마칠 수 없으면 기존 2페이즈 전용 축소안을 적용하고, 체크리스트에서 1페이즈를 완료로 표시하지 않는다. 성공 후 직접 휴지통 비우기·재등장 없음 등 확정 흐름은 축소를 이유로 바꾸지 않는다.

## 13. 간헐적인 마우스 끊김 적용 순서 [제외]

2026-10-31 최신 사용자 지시에 따라 현재 제작 범위에서 제외한다. 창 조작·퍼즐·보스전과 게임 완주를 우선하며 이 부가 연출의 구현·성능 측정·설정 메뉴는 후속 필수 작업으로 남기지 않는다. 이전 단계별 계획은 폐기하고, 관련 시험 구현은 개발 기록으로만 보관한다. 정리 상태는 [체크리스트 23장](IMPLEMENTATION_CHECKLIST.md#23-간헐적인-마우스-끊김-구현-계획--2026-10-31)을 따른다.
