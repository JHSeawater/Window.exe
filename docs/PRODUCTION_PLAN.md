# WINDOW.exe — 제작·시연 계획

> 역할: 목표 분량, 작업 우선순위, 일정과 발표·시연 순서를 관리한다.
> 기준일: 2026-10-31. 별도 표기가 없는 계획은 **[제안]**이다.
> 행사 조건은 [프로젝트 배경](PROJECT_CONTEXT.md), 담당·진행 상태는 [구현 체크리스트](IMPLEMENTATION_CHECKLIST.md)에서 관리한다.

## 1. 목표와 우선순위

핵심 플레이가 실제로 작동하는 짧은 한 판을 목표로 한다. **[확정 — 현재 설정]** 앞 퍼즐의 열쇠 획득에서 복원 함정과 보스전을 거쳐, 직접 휴지통 비우기로 프로그램과 희생자들을 삭제한다. 2페이즈 피격은 다운로드를 유지한 채 즉시 리스폰하고, 다운로드가 완료되면 별도 배드 엔딩으로 종료하며 리스폰하지 않는다. 구출·자리 교환 경로는 만들지 않는다.

**[확정 — 사용자 답변]** 보스전은 1·2페이즈 모두 목표로 하고 2페이즈부터 확보한다. 구현 우선순위와 축소 원칙은 [보스전 기획 9장](BOSS_FIGHT.md#9-우선순위-제안), 담당·완료 조건은 체크리스트 18장, 착수 후 단계는 이 문서 12장을 따른다. **현재는 계획 단계이며 별도 명령 전에는 구현하지 않는다.**

## 2. 범위 조정 [제안]

- 매 단계에 시작·전진·회피·실패/재시작·성공이 있는 작은 플레이 흐름을 확보한다.
- 보스전 일정이 부족하면 1페이즈를 빼고 2페이즈를 남기는 기존 축소안을 적용한다. 조작 유언도 2페이즈로 옮긴다.
- 관문 D·보스 직접 사격·바퀴당 속도 증가·분위기 연출·사운드 다듬기는 보스전 기획의 선택 범위다.
- 앞 퍼즐의 파일 조사·비밀번호·엿보기 해법은 별도 담당이 정한다. 과거 반환 순서를 현재 삭제의 선행 조건으로 복원하지 않는다.
- 보스전 직전 연출·성공 엔딩·다운로드 완료의 별도 배드 엔딩 장면은 다른 담당의 범위다. 보스전은 진입/성공/배드 엔딩 신호와 표시 인계를 연결한다.
- 일반 창의 시작 메뉴·트레이·시계·앱 고정 같은 후속 기능을 보스전의 선행 조건으로 잡지 않는다.
- 실제 OS 종료 감지나 작동하는 작업 관리자·전원 UI는 범위에 넣지 않는다.
- 공통 글꼴과 CRT의 기존 구현을 사용하되, 새 유언·위험 신호의 가독성과 실제 게임 상태 연결은 별도로 확인한다.

### 결과별 작업량

| 결과 | 필요한 제작 |
|---|---|
| 일반 실패·재도전 | 1페이즈 재시작은 기존 규칙 유지. 2페이즈 피격은 재도전 화면 없이 시작 순간으로 즉시 복구하고 다운로드 진행도·남은 시간 유지 |
| 다운로드 완료 배드 엔딩 | 여러 번의 시도가 공유하는 총 시간이 다 되면 전투를 끝내고 별도 배드 엔딩 담당에게 한 번 인계. 자동 리스폰 없음 |
| 복원 취소 | 2페이즈의 포획·보스 드롭, 다운로드/공격/실패 판정 중단, 완료 신호 인계 |
| 삭제 성공 엔딩 | 다른 담당이 직접 휴지통 비우기와 희생자/프로그램 삭제·정상 바탕화면 복귀를 연결. 프로그램 재등장 없음 |

## 4. 발표·시연 흐름 [제안]

1. 파일 조사·엿보기로 창이 공간을 비춘다는 점과 열쇠 획득을 짧게 보여 준다. 앞 퍼즐의 확정 해법은 담당과 맞춘다.
2. 휴지통 복원으로 강제 다운로드가 시작되고 눈알 연출로 함정이 드러난다.
3. 보스전에서 창을 늘리고 휴지통을 끌며 전진하는 조작을 보여 준다. 두 페이즈는 보스전 기획의 목표 길이 안에서 시연한다.
4. 복원 취소 뒤 플레이어가 직접 휴지통 비우기를 실행하고 정상 바탕화면으로 돌아오는 성공 엔딩으로 마무리한다.
5. 리허설·개발용으로는 보스전 바로 시작·페이즈 건너뛰기·무적·다운로드 멈춤을 준비한다. 실제 발표 사용 여부는 리허설에서 정하며 활성 표시는 숨기지 않는다.

빠른 포획으로 일자 벽을 생략할 수 있으므로, 벽 회피를 보여 줄 리허설에서는 임계값을 넘은 뒤 벽을 기다려 최소화한다. 이를 위해 실제 게임 진행을 강제로 잠그지는 않는다.

### 질의 대비 한 줄 답변

> WINDOW.exe는 전 사용자의 흔적을 조사하다 복원 함정에 빠진 플레이어가, 창을 시야이자 몸으로 조작해 프로그램을 휴지통에 되돌리고 삭제하는 게임입니다.

## 5. 10/30 사용자 담당 구현 순서 [제안]

오늘의 결과물은 **아이콘을 선택·실행·이동할 수 있고, 배치와 입력 충돌이 처리되며, 창 시스템에 열기 요청을 전달하는 데스크톱**이다. 계획 보고 후 구현·검증과 커밋·푸시까지 진행했다. 아래는 작업 순서를 보존한 계획이며, 실제 확인 결과와 완료 상태는 [체크리스트](IMPLEMENTATION_CHECKLIST.md)의 8장에서 관리한다.

| 순서 | 진행할 작업 | 확인할 결과 |
|---|---|---|
| 0. 작업 경계 준비 | 코드·프리팹·데이터·검증 씬의 배치와 공유 경로를 정하고, 팀원과 고정 식별자·열기 요청·화면 기준을 맞춤 | 창이 없어도 임시 수신기로 개발 가능. 제외된 스크립트 없이 씬만 공유되는 상황 방지 |
| 1. 데스크톱 뼈대 | 바탕화면과 아이콘 영역 구성, 아이콘 공통 프리팹·데이터 준비, 테스트 아이콘 3개 이상 배치 | 데이터에 따라 이름·이미지·식별자가 다른 아이콘이 보이며 초기 배치가 겹치지 않음 |
| 2. 선택과 열기 | 선택·선택 변경·빈 공간 선택 해제, 더블클릭 시 식별자 전달 | 임시 수신기에서 올바른 식별자를 한 번 받음. 표시 이름을 바꿔도 연결 유지 |
| 3. 드래그와 배치 | 이동 시작 거리, 잡은 지점 유지, 화면 좌표 변환, 경계 제한, 겹침 검사와 위치 확정 | 드래그 후 실행 오인 없음. 화면 안의 유효한 위치만 확정. 원위치 복귀 방식은 개발 가이드의 제안 |
| 4. 입력 충돌 확인 | 먼저 입력을 가로막는 테스트 패널로 가림 동작 확인, 이후 실제 창으로 재확인 | 창 클릭이 뒤쪽 아이콘·바탕화면에 전달되지 않고 창 조작이 아이콘 위치를 바꾸지 않음 |
| 5. 실제 창 연결 | 임시 수신기 대신 팀원 창 시스템에 열기 요청 연결 | 새 창 열기·기존 창 앞으로 가져오기·최소화 복원·닫은 뒤 재열기를 함께 확인 |
| 6. 최종 확인 | 체크리스트 순서로 조작하고 서로 다른 해상도·UI 배율과 실행 빌드에서 확인 | 확인한 작업만 완료 체크. 창 통합을 못 했다면 데스크톱 단독 확인과 통합 미확인을 구분해 기록 |

후속 작업은 팀원과 열기 요청·화면 기준을 맞추고 실제 창 시스템을 연결한 뒤, 중복 방지·최소화 복원·재열기·아이콘 위치 유지·입력 가림을 함께 확인하는 순서로 진행한다. 통합 뒤에는 테스트를 마친 다음 빌드를 만들어 같은 항목을 확인한다. 구현 구조와 연결 경계는 [개발 가이드 7~8장](DEVELOPMENT.md#7-데스크톱-구현-구조와-처리-순서)에서 관리한다.

위 표는 최초 단일 선택 구현의 순서다. 후속 요청인 다중 선택은 아래 6장 순서로 추가 구현했다. 격자 정렬·우클릭·앱 재실행 후 위치 저장·실제 삭제 판정과 게임 퍼즐은 이번 추가 작업에 포함하지 않는다. 제공된 배경·아이콘은 공통 프리팹과 데이터에 이미 연결했으며, 추가 게임 콘텐츠와 리소스는 기존 후속 범위를 따른다.

## 6. 추가 구현 — 드래그 영역 선택

10/30 사용자 요청으로 수립한 계획을 이후 구현 요청에 따라 진행했다. 아래는 구현한 작업 순서이며, 완료 여부와 검증 결과는 [체크리스트 2-1장](IMPLEMENTATION_CHECKLIST.md#2-1-추가-구현--드래그-영역으로-여러-아이콘-선택)과 9장에서 관리한다. 추가 구현과 역할별 정리는 이번 공유 변경에 포함한다.

| 순서 | 작업 | 확인할 결과 |
|---|---|---|
| 1. 선택 상태 확장 | 컨트롤러의 단일 선택을 선택 집합과 대표 아이콘으로 확장. 누르기·클릭 완료·드래그 시작의 처리를 분리 | 기존 단일 클릭·더블클릭을 유지하고 여러 아이콘을 동시에 강조할 수 있음 |
| 2. 선택 상자와 판정 | 빈 바탕화면의 드래그 입력, 사방향 사각형 계산, 실시간 교차 판정, 입력을 막지 않는 표시 추가 | 작은 흔들림은 클릭, 충분한 이동은 영역 선택. 놓은 뒤 선택 유지 |
| 3. 입력 충돌·취소 처리 | 아이콘에서 시작한 드래그와 영역 선택을 구분. 클릭 연속 상태 초기화, 포커스 상실·Escape·비활성화 시 복원 | 선택 상자가 남지 않고 의도하지 않은 열기 요청이나 창 조작이 발생하지 않음 |
| 4. 선택 후 이동 보완 | 선택된 아이콘을 누를 때 집합 유지, 이동 없이 놓으면 단일 선택. 이어서 상대 간격을 유지하는 묶음 이동 구현 | 다중 선택이 드래그 시작과 동시에 풀리지 않음. 경계는 묶음 전체로 제한하고 충돌 시 전부 복귀 |
| 5. 확인과 문서 갱신 | 추가 테스트와 기존 14개 테스트 회귀 확인 후 Windows 빌드·수동 조작. 실제 팀원 창 연결 여부도 구분 | 1280×720·1920×1080에서 선택 상자·배율·묶음 배치 확인. 검증한 항목만 완료 표시 |

영역 선택과 묶음 이동을 연결하고, 공유 씬의 두 해상도 입력 시험까지 수행했다. 다음 우선순위는 7장의 최소 작업 표시줄과 실제 창 통합이다. Ctrl·Shift·Ctrl+A, 격자 정렬, 다중 실행·삭제는 별도 후속 범위로 둔다. 세부 입력·충돌 규칙과 변경 파일은 [개발 가이드 9장](DEVELOPMENT.md#9-드래그-영역-선택-구현)을 따른다. 창 이동·크기 조절·최대화·최소화는 팀원 담당을 유지한다.

후속 사용자 요청으로 Assets 역할별 정리도 수행했다. 새 코드·에셋은 [개발 가이드의 폴더 배치](DEVELOPMENT.md#assets-폴더-배치-확정--사용자-지정)를 따르며, 이동 재검증은 [체크리스트 10장](IMPLEMENTATION_CHECKLIST.md#10-assets-역할별-정리와-재검증)에서 관리한다. 게임 기능의 우선순위와 담당은 유지한다.

### 바로 착수할 단위

사용자 요청으로 **최소 작업 표시줄 UI와 창 연결**에 착수했던 순서를 아래에 보존한다. 1~4의 임시 단계 결과는 체크리스트 11장, 이후 실제 창 연결인 5의 일반 흐름은 12장, 추가 검수에서 발견한 미해결 예외는 15장에서 관리한다. 현재 작업을 임시 제공자 단계로 되돌려 해석하지 않는다. 창의 이동·크기·최소화·최대화와 활성 상태는 실제 창 시스템이 관리한다.

| 순서 | 착수 단위 | 다음으로 넘어갈 기준 |
|---|---|---|
| 1 | 연결 계약 초안·정책 정리 | 임시 제공자와 UI가 사용할 식별자·조회·알림·요청 계약을 정하고, 팀원 API에서 미확인인 대응 항목을 남긴다. 창 구현 완료를 기다리지 않고 2~4로 진행 가능 |
| 2 | 공통 작업 영역·하단 바 | 공통 영역을 계산해 데스크톱에 먼저 적용하고 창 시스템의 연결 지점을 준비한다. 기존 공유 씬에 구성·참조를 보존해 추가하며 실제 창 제약 적용은 5에서 확인 |
| 3 | 목록과 버튼 동기화 | 미리 열린 창부터 등록하고 변경·제거·재구독·초기화에 맞춰 표시한다. 버튼 수 초과와 긴 제목도 접근 가능하게 한다 |
| 4 | 활성화·최소화·복원 | 클릭 직전 상태와 허용 조작에 따라 요청하고 확정 상태를 표시한다. 다음 활성 창·최대화 복원·요청 거부를 확인한다 |
| 5 | 실제 창 통합·회귀·빌드 조작 | 임시 수신기를 실제 창 어댑터로 연결하고 기존 데스크톱 동작을 회귀 확인한다. 두 해상도의 공유 씬과 Windows 실행 빌드에서 실제 입력을 확인한다 |

연결 계약과 초기 수치는 [개발 가이드](DEVELOPMENT.md#작업-표시줄-연결-계약-제안), 상세 작업·검증은 [체크리스트 2-2장](IMPLEMENTATION_CHECKLIST.md#2-2-다음-착수--최소-작업-표시줄-제안)을 따른다. 팀원 창이 준비되기 전에는 같은 계약의 임시 상태로 2~4를 진행할 수 있으나, 실제 창 통합과 빌드 조작 확인은 별도로 남긴다. 게임 재시작·종료 화면과 엿보기 단서 도달 검증은 해당 기능 통합 시 이어서 확인한다.

팀원 API 대조와 Git 병합은 완료했고, 렌더링과 최소 입력 차단을 준비한 뒤 어댑터를 먼저 연결하고 다중 창 입력을 확장한다. 다음 구현은 8장 순서로 진행한다. 현재 임시 단계의 결과는 [체크리스트 11장](IMPLEMENTATION_CHECKLIST.md#11-작업-표시줄-임시-제공자-단계-구현검증), 병합 검토는 12장에서 관리한다.

**[확정 — 사용자 지정]** 별도 창 숨김은 첫 구현에서 보류하고 기록만 남긴다. 모달 소유 창의 활성화 요청을 해당 모달로 전달하는 예외는 명시하며 소유 창 최소화는 거부한다. 전체 조작 잠금·제거된 창에는 예외를 적용하지 않는다. 세부 계약의 원본은 개발 가이드, 보류 기록과 완료 확인은 체크리스트에서 관리한다.

이 최소 작업 표시줄 단계에서는 시작 메뉴·트레이·시계·앱 고정·전환 애니메이션을 후순위로 두었다. 이후 시작 버튼 요청의 추가 계획은 9장을 따른다. 검수 보완은 기존 최소 범위의 동작·연결·완료 조건을 구체화한 것이며 새 게임 규칙이나 담당의 확정을 뜻하지 않는다.

이 흐름을 확인한 뒤 **진행 상태 + 메모·설명서·사진 데이터와 비밀번호 판정**으로 넘어간다. 초기 검증용 암호 `1030`과 내용은 GDD 7-1장의 제안으로 유지한다. 기존 창 연결 경로에 사진 잠금 화면을 얹고, 데이터·판정 검증과 실제 화면 통합 확인은 구분한다.

게임 콘텐츠의 첫 작은 흐름은 **메모 열기 → 날짜 확인 → 사진 비밀번호 해제 → 닫고 다시 열어 해제 상태 확인**이다. 그다음 게임의 핵심 차별점인 엿보기로 이어간다. 시작 오류·실행 전 경고는 게임 진입과 프로그램 실행을 연결할 때 함께 넣고, 긴 도입 연출은 후속으로 다듬는다.

### 연결 전에 맞출 사항

- 팀원과 창 연결 계약·표시 및 허용 조작 정책·WindowLayer·공통 작업 영역·Canvas 배율을 맞춘다. 실제 조회·알림·요청 형식과 기존 열기 이벤트의 대응은 [개발 가이드](DEVELOPMENT.md#작업-표시줄-연결-계약-제안)를 따른다.
- 엿보기 창의 최대화·최소화·리사이즈 허용 범위는 GDD의 미정 사항이다. 우선 기본 크기와 창 이동으로 단서에 도달하는 검증을 만들고, 허용 범위는 통합 전에 정한다.
- 휴지통은 현재 아이콘 겹침 검사에서 일반 충돌 대상이다. 게임의 드롭 의도를 판정한 뒤 일반 배치 확정을 처리하도록 분리한다. **[제안]** 첫 삭제 구현은 WINDOW.exe 하나만 선택해 끌었을 때로 제한하고, 다중 선택 드롭은 삭제하지 않고 전체 복귀·안내한다. 영구 배치에서 아이콘 겹침을 허용하지 않는다.
- 1~6의 콘텐츠·퍼즐·엔딩 세부 규칙은 GDD의 기존 [제안]·[미정] 상태를 유지한다. 작업 순서 정리만으로 기획을 확정하지 않는다.

### 한 판을 연결한 뒤 할 일

구출 분기의 자리 교환 배드 엔딩, 오염도·시선 위협, 사운드·글리치 연출은 후속 순서로 둔다. 제공 폰트 적용·추가 아트 다듬기는 실제 콘텐츠 화면을 읽을 수 있는지 확인하며 진행한다. Ctrl·Shift·Ctrl+A, 우클릭 메뉴·격자 정렬·위치 영구 저장은 계속 후순위로 유지한다.

| 7. 실행 파일·인계 | Windows 빌드·시작·직접 마우스 확인과 씬/메타/문서 마무리 | 검증한 내용과 남은 게임 통합을 구분해 인계하고 파일 조사/비밀번호 작업으로 진행 가능 |

첫 화면 확인은 메모장 본문·제목의 표시이며, 그 직후 **메모 아이콘 → 실제 창 → 실제 작업 표시줄 → 최소화/복원 → 닫기**의 작은 흐름을 완주한다. 단계 1에서 코드로 생성해 표시를 확인하더라도 단계 2는 실제 아이콘과 버튼 입력으로 확인한다. 이 연결의 관리자 상태·표시 순서를 뒤 입력 판정의 원본으로 사용하며 임시 모델로 이중 관리하지 않는다. 전체 완료는 3~7의 확장·예외·회귀·빌드 확인까지 마친 상태다.

변경은 기준선/직렬화 → 창 하나의 표시 → 실제 최소 연결 → 입력 → 좌표 제약 → 다중 창/수명 → 회귀/빌드/문서처럼 검토 가능한 단위로 나누는 안이다. 각 단위에서 관련 검증을 마치고 다음으로 진행하며, 커밋·푸시는 사용자 요청을 따른다. 작은 화면·창 겹침·소유 입력 문제가 남은 상태에서 퍼즐 로직을 먼저 얹지 않는다.

기술 설계와 예상 변경 파일은 [개발 가이드 10장](DEVELOPMENT.md#10-창데스크톱-호환-구현-계획-제안), 실제 진행·완료 조건은 [체크리스트 12-1장](IMPLEMENTATION_CHECKLIST.md#12-1-실제-호환-구현과-완료-조건-제안)을 원본으로 관리한다. 일반 창 검증에서의 최대화·최소화 허용을 엿보기 창의 게임 규칙으로 확정하지 않는다.

## 9. 좌하단 시작 버튼 추가 [제안]

2026-10-31 사용자 요청으로 좌하단 시작 버튼의 후속 계획을 추가했다. 현재 일반 창 호환·공통 글꼴이 있는 작업 트리를 기준으로 하며 기존 통합을 다시 만들지 않는다. 버튼과 작은 실행 메뉴를 한 작업 단위로 구현하는 안이다. 시간별 일정이나 게임 퍼즐보다 높은 영구 우선순위를 확정하는 것은 아니다.

| 순서 | 작업 | 단계 완료 기준 |
|---|---|---|
| 1. 고정 영역 | 시작 버튼과 창 목록 영역 분리, 목록 ScrollRect/화살표 참조·너비 계산 수정 | 창 수·넘침과 관계없이 시작 버튼이 좌하단에 보이고 목록과 겹치지 않음 |
| 2. 메뉴와 입력 | 작은 Overlay 메뉴·외부 닫기 영역, 라우터 소유권·클릭 완료·취소 연결 | 토글/바깥 클릭/Escape 닫기, 뒤쪽 입력 차단, 기존 드래그 소유 유지 |
| 3. 실제 실행 | 명시 콘텐츠 목록과 공통 런처 연결, 잠금·모달·등록 여부 검사 | 새 창 열기/활성화/최소화 복원을 한 경로로 처리하고 우회 실행·중복 생성 없음 |
| 4. 씬·검증 | 새 씬/기존 갱신 연결, 두 해상도·회귀·빌드·실행 파일 확인 | 반복 갱신/재열기 정상, 지정 환경의 검증 결과와 미확인 항목을 구분해 기록 |

최초 메뉴 항목은 기존 메모·사진·인터넷으로 제한하는 안이다. 전원·강제 종료·게임 재시작과 검색·앱 고정·하위 메뉴는 별도 작업으로 남겨 핵심 게임 제작 분량이 커지지 않게 한다. 세부 기술 규칙은 [개발 가이드 12장](DEVELOPMENT.md#12-좌하단-시작-버튼-구현-계획-제안), 완료 확인은 [체크리스트 14장](IMPLEMENTATION_CHECKLIST.md#14-좌하단-시작-버튼-구현-계획--2026-10-31)에서 관리한다. 이번 요청에서는 계획 문서만 갱신한다.

## 10. 전체 검수 문제 수정 순서 [제안]

2026-10-31 작성한 수정 순서의 원안이다. 후속 사용자 지시로 검토 보완을 포함해 이 순서에 따라 구현에 착수했고, 실제 완료·검증 결과는 체크리스트 15-4장에서 관리한다. 시간별 마감이나 시작 버튼/게임 콘텐츠의 영구 우선순위는 변경하지 않는다.

| 순서 | 작업 단위 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 0 | 기존 변경 보존·공유 회귀 사례 준비 | 현재 코드/씬을 보존하고 세 재현이 수정 전 코드에서 실패함을 확인. 이전 63개 통과와 새 실패를 구분 |

| 4 | 전체 시험·지정 씬 빌드·직접 조작·문서 반영 | 기존/신규 회귀, 두 해상도의 입력·기동, 실제 환경의 실행 파일 직접 조작을 확인하고 남은 검증을 구분해 보고 |

## 11. 전체 화면 CRT 노이즈 적용 순서 [제안]

2026-10-31 작성한 제공 소스 개선안을 후속 사용자 지시에 따라 구현에 착수했다. 아래는 진행 순서의 원안이며 후속 검토에 따라 4단계에 측정용 Development Player 생성, 5단계에 최종 빌드를 구분했다. 실제 완료·남은 검증은 체크리스트 16장에서 관리한다. 기존 창·작업 표시줄·공통 글꼴과 QA 수정 결과를 기준으로 삼고, 게임 한 판·시작 버튼의 우선순위나 시간별 마감을 새로 확정하지 않는다.

| 순서 | 작업 단위 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 0. 소스·출력 기준선 | 로컬 제공 소스 보존, 역할별 경로·공유 의존성 정리, 실제 URP 셰이더 확인 | 컴파일·단일 전체 화면 출력과 기존 화면 보존 확인. 조회 시간초과를 통과로 처리하지 않음 |

휘어짐·색수차·화면 찢김을 같은 작업에 추가해 범위를 넓히지 않는다. 약한 기본 효과와 제어 API를 먼저 검증하고, 게임 진행 시스템이 준비되면 오염도 전달·재시작 초기화·실패/엔딩 화면의 적용 범위를 별도로 연결한다. 시선 위협 미채택 시 오염도 0을 유지하는 기존 제안도 그대로다.

기술 계약과 초기 시간값·파일 배치는 [개발 가이드 14장](DEVELOPMENT.md#14-전체-화면-crt-노이즈-구현-계획-제안), 담당 제안·작업·완료 조건은 [체크리스트 16장](IMPLEMENTATION_CHECKLIST.md#16-전체-화면-crt-노이즈-구현-계획--2026-10-31)에서 관리한다. 이 계획의 UI 검증을 게임 오염도·게임 오버 구현 완료로 바꾸지 않는다.

0단계에서 1페이즈 경로의 수치 충돌을 먼저 찾고 3단계 시작 시 단순 도형의 실제 조작으로 확인한 뒤 전체 표시를 제작한다. 2페이즈를 먼저 확보하는 우선순위는 유지한다. 검토 후 사용자 결정의 원본은 [BOSS_FIGHT 13-1장](BOSS_FIGHT.md#13-1-사용자-답변으로-확정한-사항--2026-10-31), 세부 경합·시간·인계 검증 방식은 개발 가이드 17장에 둔다.

**축소 기준:** 2단계를 먼저 시연 가능한 상태로 보존한다. 남은 일정으로 1페이즈 경로와 전체 검증을 함께 마칠 수 없으면 기존 2페이즈 전용 축소안을 적용하고, 체크리스트에서 1페이즈를 완료로 표시하지 않는다. 성공 후 직접 휴지통 비우기·재등장 없음 등 확정 흐름은 축소를 이유로 바꾸지 않는다.
